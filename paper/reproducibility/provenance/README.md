# Allen--Cahn evidence provenance bundle

This directory records the evidence used for the DIM adaptive-weighting
manuscript. It does not launch training or recompute a prediction. The v2 audit
record binds four formal claims to 17 aggregate metrics, 315 distinct
mechanism/domain prediction records, 258 evaluations, 57 final-iterate
checkpoints, 57 exact configuration entities, 57 completed runs, four spatial
domains, ten controller traces and two locked protocols.

## Formal claim boundary

| ID | Formal claim | Inferential status |
|---|---|---|
| C1 | Grouped adaptive loss weighting reduced final-network relative $L^2$ retention error over the fitted interval relative to fixed coefficients in all ten paired seeds; both arms used the same positive rate-normalised RK4 term. | Frozen secondary matched contrast and diagnostic outcome. |
| C2 | The data did not demonstrate a reduction on direct validation, direct test, numerical-continuation test or terminal state. | Frozen secondary contrast; non-improvement is not equivalence. |
| C3 | The 4-, 8- and 12-block runs did not show growing support for an adaptive final-network fitted-interval retention advantage. | Three-seed development evidence only. |
| C4 | The controller respected its coefficient-budget invariants, assigned a majority of the active later-block constraint budget to replay, and recorded no guard triggers. | Descriptive diagnostic only. |

Fixed RK4 versus zero-RK4 is deliberately excluded from the formal C1--C4
graph because it belongs to the companion RK4 analysis. The copied source
summaries retain those contrasts as contextual evidence.

## Main files

- `allen_cahn_audit_record.json`: JSON Schema-validated machine audit.
- `audit_record.schema.json`: JSON Schema Draft 2020-12, version 2.0.0.
- `claim_evidence_matrix.csv`: C1--C4 directions and supporting/limiting IDs.
- `query_claim_evidence.py`: independent claim traversals plus explicitly labelled CQ1--CQ6 coverage.
- `competency_query_results.json`: stored claim paths and answers to CQ1--CQ4; CQ5--CQ6 list delegated validation and declared gaps, not unperformed success.
- `ro-crate-metadata.json`: canonical RO-Crate 1.3 descriptor. The
  byte-identical `ro-crate-metadata.jsonld` file is a compatibility alias; it
  is not the descriptor ID.
- `evidence/evidence_sources.json`: portable 17-source register whose
  `bundle_path` entries all exist below `evidence/source_registry/`.
- `evaluations/`: copied per-run record, metrics, completion, controlled-run
  and grouped-controller diagnostic records.
- `validation_report.json`: formal validation result written only after
  packaged and external-workspace verification both pass.
- `build_provenance.py`: deterministic builder for the bundle.
- `profile_validation.py`: generic in-memory schema, links, domain, evidence-status and PROV consistency checks.
- `validate_provenance.py`: generic-profile CLI plus the full frozen-study, numerical-source, integrity and packaging checks.
- `test_profile_validation.py`: regression tests, including a synthetic two-run/one-claim negative-result control (not new experimental evidence).
- `audit_comparison_spec.json` and `audit_comparison.py`: frozen nine-case comparison; results and the generated manuscript table are separate derived outputs.

The machine graph contains a W3C PROV class/relation projection with `Entity`,
`Activity` and source-identified software `Agent` records. Each exact
configuration is a hash-bound entity used by its training activity, and each
run records source-linked start time, training completion time and duration.
Each checkpoint is generated by training. Each prediction has its own
prediction activity that uses its checkpoint and explicit temporal, native
spatial and evaluation spatial domains. Numerical continuation uses the
terminal-state prediction as its upstream state. Each evaluation has a
separate activity that uses its prediction, reference field and checkpoint.
The ten grouped runs have controller-trace entities distinct from field
predictions. Aggregate metrics have synthesis activities, and the C1--C4
tables and figures are explicitly derived from their claims and metrics.

## Explicit evidence limitations

- `checkpoint_file_sha256` is `null` for every run because no serialized
  checkpoint-file digest was preserved. `parameter_state_sha256` is the
  canonical final-parameter-state digest read from the copied controlled-run
  record at `/final_parameters_sha256`; it is not a checkpoint-file hash.
- The long-sequence study has no separate validation split. Its runs declare
  `unavailable_prediction_roles: ["validation"]`; no validation result is
  imputed.
- Direct fields and terminal states are present in `predictions.npz`. For the
  confirmatory campaign, DOP853 integrates the terminal state on the native
  256-node periodic FD grid, interpolates to the 1024-node reference grid for
  scoring, and preserves `continued_prediction` in `evaluation/fields.npz`;
  all 30 field files are recorded as external artifacts with their original
  `fields_sha256`. For the long-sequence campaign, integration and scoring are
  both on the 256-node grid after the 1024-node reference is periodically
  interpolated down to 256. Those 27 continuation fields were not persisted:
  their prediction records use `status: field_not_persisted` and a null output
  artifact, while `metrics.json` remains solely the evaluation source.
- Raw prediction and reference arrays remain in the source study archive.
  They are referenced by bundle-relative workspace paths and SHA-256 rather
  than duplicated. A standalone copy can validate every packaged record while
  deliberately skipping these external paths.
- No reuse licence has yet been assigned to the bundle. The RO-Crate licence
  entity records that status and grants no reuse rights; source components
  retain their own terms.

## Validation

The generic layer accepts differing study counts, arm labels, claim identifiers
and outcome directions within the supported profile vocabulary. It checks
metadata only and does not read result bytes or recompute numerical values:

```bash
python validate_provenance.py --mode profile
python validate_provenance.py --mode profile --record another_record.json
python -m unittest -v test_profile_validation
```

This version still describes completed final-iterate sequential runs and
periodic one-dimensional spatial domains. It is not a universal workflow
schema. Missing required fields are errors; an explicitly empty limiting-
evidence list is allowed. No metadata checker can establish that a complete-
looking disclosure or scientific statement is truthful.

The default study mode retains every frozen Allen--Cahn assertion, including
the seed matrix and the C1--C4 outcome boundaries, and checks packaged file
bytes. It never changes the formal report:

```bash
python validate_provenance.py
```

In the source workspace, verify the 57 raw prediction arrays, 30 confirmatory
continuation-field arrays and four locked reference arrays, then write the
formal report:

```bash
python validate_provenance.py --verify-external --write-report
```

`--write-report` requires `--verify-external`; this prevents a standalone run
from replacing an external-verified report with a weaker result. The formal
report stores separate `packaged` and `external_workspace` integrity modes
and `generic_profile` and `frozen_study_regression` layers. The frozen-study
assertions do not define general profile validity.

Claims C1--C4 and competency questions CQ1--CQ6 have different meanings.
A claim traversal is identified as `claim-evidence:C1`, for example, and can
answer several questions. CQ1 returns protocol/configuration/seed/checkpoint,
CQ2 prediction mechanism and domain, CQ3 reference and evaluation details,
and CQ4 supporting/limiting evidence and status. CQ5 requires the separate
integrity validator. CQ6 reports declared unavailable roles and delegates
missing-field checks to the schema validator; legacy gaps remain documented
in the supplementary audit.

Run all claim traversals or one selected claim with:

```bash
python query_claim_evidence.py
python query_claim_evidence.py --claim C2
```

The returned paths operationalise:

```text
claim -> supporting/limiting metric or evaluation
      -> prediction/evaluation/controller trace
      -> run -> exact configuration -> locked protocol
```

The scientific record retains 57 configurations, 57 runs, 57 checkpoints,
four spatial domains, 315 predictions, 258 evaluations, ten controller traces,
17 metrics and four claims. The regenerated report records exact artifact and
PROV counts. Six newly hash-registered validation/query/specification sources
increase the inventory to 288 packaged and 91 external artifacts; they do not
add training runs or scientific claims.
